# EnvOpt 的 methodology：应该把哪些设计讲出来

后续定位更新：根据 RSIBench-Data 原文与用户进一步反馈，主叙事已提升为 data-centric research for RSI，World–Scene–Task 是主要方法结构。下面分析的正确性、校准和两种反馈仍然成立，但最新主图将检查收成小 gate，不再让它与 RSI/层级结构争夺注意力。参见 [rsi_positioning_zh.md](rsi_positioning_zh.md)。

## 判断：主图需要压缩信息层级，而不是压缩掉方法

“生成环境 → 生成任务 → 训练模型”的图只能说明系统做了什么，不能说明为什么需要 EnvOpt。漂亮的图标也不能补上这个缺口。更准确的中心问题是：**如何在不断迭代中，持续提供既保持任务含义、又覆盖目标决策、还对当前学生有训练价值的可执行经验？**

因此，主图应该有一个明确的优化对象和两个反馈尺度。对象是 World / Scene bank / parameters / mixture 组成的任务生成过程；内环固定学生，检查并校准候选环境；外环更新学生，再用固定 dev 检验实际迁移。图中还要让人看出反馈如何决定修改方向，而不是所有失败都流向一个泛化的“improve”箭头。

以下分清三个层级：**当前代码的机制**、**GUIDE 已要求但尚未系统验证的策略**、**建议新增并做消融的研究设计**。三个层级都值得讨论，但不能在当前方法图中用同一种实线表示它们已经完成。

## 1. 当前最值得进入主图的五个设计

| 设计 | 它改变了什么 | 为什么对 iterative data evolution 重要 | 当前证据 |
| --- | --- | --- | --- |
| 以可复用 Scene 为编辑单元 | 同时编辑交互机制、task constructor 和 reusable verifier；任务实例通过 goal data 绑定 | 一次改动影响后续一整个任务分布，能累积机制，而不只累积一批样本 | `generation/scene.py`, `core.Task.bind`, `propose.propose` |
| 机制覆盖与采样配比分开 | 先建立 bank 的支撑，再分配本轮预算；缺机制可以扩展，已有机制可以调参数或权重 | 重复采样一个容易造的任务类型不能替代缺失能力；也不能把扩展 bank 等同于均匀训练全部内容 | `control/coverage.py`, `auto.scene_cold_start`, `plan_for` |
| 一份 goal，多个受约束的视图 | request、合法 user facts、verifier 共享目标含义，但 agent/user 不获得相同信息 | 防止任务、用户和判分描述三套不同世界；澄清和信息搜集必须仍是学生要做的事 | `GUIDE` §1、`user_facts`、neutral examples；语义完全一致不是自动证明 |
| 正确性与学习信号分开验证 | 先局部环境/奖励 contrasts，再对固定学生做 fresh repeated probe | 无 reward 可能是环境坏、判分有争议、信息不可得，也可能只是学生不会；修改方法应不同 | `contracts.validate`, `calibration.summarize`, `auto.calibrated_edit` |
| 内外两环与独立的数据角色 | 内环不更新学生；通过后生产新训练任务，外环训练并固定 dev 评测 | 避免模型变化与环境变化混在一起，也避免拿变化中的 synthetic reward 充当性能进步 | `control/auto.py`, `production.py`, `lab/rl/rewards.py` |

其中，真实 user-side effects、正权重 partial rewards 与 hard guards、版本冻结、预算保留和 no_training 都是重要的支撑设计。主图用一两句标注即可，详细接口放在正文。调度器、端口、GPU 数量、主/子代理的具体实现不需要进入方法主图。

## 2. 三种问题必须对应不同编辑方向

**覆盖缺口 → 扩展机制。** 例如 dev 失败需要跟踪相对路径和跨轮 cwd，但训练环境只有固定 ID 的平面记录；这时提高任务数量或调整 success-rate band 都没有直接解决问题。应实现相应的状态与引用语义，再生成同类决策。

**语义缺陷 → 修复有问题的组件。** 例如用户说“已重启”却没有真实动作；verifier 把 API `ok` 当业务成功；任务只要求提交，却额外要求指定的最后一句话。这些不是“学生太弱”，不能通过降低业务难度或修改旧标签掩盖。若是 reviewer/verifier 争议，先调查哪一侧错误。

**合法但缺乏有效学习信号 → 调整负担与分配。** 在保留目标决策的前提下，减少待处理实体、降低无关信息量、缩短重复工作；饱和机制则可以增加必要组合或减少采样权重。这里需要关注实际失败组件，而不只是总体 reward。

当前系统的分流有实现，语义判断仍由 coding agent、局部检查和有限诊断共同完成。图中可以写“diagnose → expand / repair / calibrate”，但不能写“自动因果归因已解决”。

## 3. 最值得强化的设计候选 A：保持关键决策的 curriculum

**现有基础：** GUIDE 已要求调整可解释 workload、保持 coverage，不能靠隐藏条件或答案泄露制造难度。但没有统一的机制保持判据，不能证明每次变简单以后仍在训练原来的能力。

**建议：** 对每个 Scene 的修改，区分关键决策和可调负担。关键决策可以是“必须从真实信息辨别目标”“必须向用户询问一个私有偏好”“必须区分暂存和提交”；负担可以是实体数、重复操作数、依赖长度、无关候选数。无需新增一个大型 DSL，可以先在已有 edit plan 中记录这些约束，并由该 Scene 的局部对照与固定诊断案例检查。

概念上可写为 `S(mechanism, workload, seed)`：改变 workload，但保持使目标决策必要的信息/状态关系。这个写法是研究视角，不是假称仓库已经实现了新的参数化 API。

| 例子 | 合理的简化 | 把训练目标一起删掉的简化 |
| --- | --- | --- |
| 用户私有目的地 | 少处理几份文件，仍保留多个可用目的地 | 只留下一个公开候选，让学生不询问也能猜到 |
| 相对路径与 cwd | 缩短目录深度，仍让后续引用依赖当前目录 | 全部替换为全局稳定 ID |
| staged update | 少修改几条记录，仍需 commit 才生效 | 让 set_value 立即生效，同时继续声称在训练 commit 语义 |
| 用户侧修复 | 减少独立故障，仍由用户真实工具操作 | 把用户动作改成 agent 可直接调用，或口头声称即修复 |

这很可能比“多轮不断把任务加难”更有论文价值：对有限能力学生，有用的 curriculum 往往是先把真实机制放到能学到的负担区间，再逐步增加复杂度。

**验证：** 对照任意 difficulty editing 与上述有约束的 editing，测关键决策是否仍必要、正式 RL 信号、同机制 held-out 迁移和工作量变化。只有更容易、没有机制保持与迁移，不能作为成功。

## 4. 最值得强化的设计候选 B：从“存在信号”到“分布中有足够相关信号”

**现有事实：** `calibration.summarize` 的准入是所有被选 Scene 都有效且 `mass > 0`。每个 Scene 默认只抽两道任务，每题两次 rollout。这个门槛可以排除完全没有实测信号的组合，但它不保证一大部分训练任务有信号，也不能区分同一 Scene 内不同变体的异质性。

**建议的研究目标：** 分开衡量覆盖预算、有效信号预算和探索预算。对关键机制或变体做分层测量，报告有信号任务所占的生产质量，结合 dev relevance、样本不确定性和成本来决定更多采样、修改程序、降低负担还是保留少量探索。

一个待验证的分配目标可以写成 `sum_j alpha_j * relevance_j * useful_signal_j / cost_j`，同时为需要保留的机制设置覆盖约束。但 relevance 和 useful_signal 都没有可靠现成 oracle；这个式子应作为实验设计的目标，而不是直接放进主文声称已实现最优调度器。

不建议立刻把 `mass > 0` 简单替换成某个很高的固定阈值。小 probe 容易漏掉真实信号，硬门槛可能加剧 no_training、浪费预算或排除难但必要的机制。应该比较当前 gate、固定覆盖下的分层 probe/分配、额外预算直接用于 RL 三种方案。所有 probe、搜索失败和生成开销都计入。

**验证：** 最核心的是 probe 对正式 production 的预测性：同机制信号是否持续、有效 groups 集中在哪里、浪费的无信号 rollout 是否减少，以及等总成本下的 test 分数。平均 synthetic reward 本身不足以回答。

## 5. 候选 C：有记忆的反例与局部回归，而不是每轮只看新样本

当前系统保存历史、提示 Evolver 回看旧失败；GUIDE 也要求修复原触发条件。但没有一个自动保证“旧反例在新版本上已复核”的通用回放系统。随机 fresh tasks 可能暂时绕开旧 bug，形成虚假的修复感。

建议为已确认的环境/verifier缺陷保留小型诊断集：完整、未完成、违规和等价完成；包括私有信息泄露与真实 user-side action 的边界。可以重复用于检查，但不作为新训练数据。verifier 也在演化时，尤其要明确固定的业务意图和预期效果，而不能用新 verifier 自己生成“正确答案”来给自己验证。

这些检查仍可能与生成器产生相关错误，所以一部分预期结果应来自独立审计或手工确认。不能称为形式化正确性或零 bug。

## 6. 候选 D：区分策略差异与模拟器/判分噪声

观察到同题 reward variation 是 group-relative 更新的必要线索，但变化也可能来自用户模拟器没有配合、工具交互不稳定或语义判分噪声。如果 Evolver 学会制造这些变化，指标会改善而任务训练价值不一定改善。

可在小规模诊断中，控制同一 Task 的初始状态与用户事实，重复判分同一条固定轨迹，并标注 reward components 的来源；对程序可判定要求优先使用实际状态和结构化 evidence。必要时做 policy sampling 与 user behavior 的交叉对照。这些额外控制应单独计成本，不默认所有训练任务都增加 teacher 或整段 judge。

## 7. 什么应写成当前 method，什么应写成待验证扩展

**现在可以进入主图和方法：** 可复用 Scene constructor/verifier、共享 goal 的 actor-specific views、覆盖 bank 与 mixture、按原因修订、局部 contrasts 与同题 probe 分工、固定学生内环、新任务训练与固定 dev 外环、证据和预算保留。

**可提高到设计原则但须限定证据：** 保持关键决策地调整 workload。这是现有 GUIDE 的策略，应写成 Evolver 的设计要求，不写成自动保证。

**作为设计候选/后续实验图单列：** 机制保持的系统检查、分层的相关信号分配、可重复诊断反例集、模拟器/判分噪声分解。当前主图不把它们画成已经存在的实现模块。若后续决定采用，再修改代码、做对照、更新正式方法。

## 8. 这如何改变 positioning

论文不应把“代码代理 + RL”当核心 novelty。更有辨识度的说法是：**在可执行机制空间中，对有语义约束的任务分布做分层适配；用内环确认候选提供什么经验，用外环检验这些经验是否教会了目标能力。**

ACE 已有正确性/复杂度/多样性的概念框架，EnvHarness 已有环境适配和 fresh validation，RODS 已有学习边界与动态数据。我们的研究需要证明，上述共享语义、可复用机制、覆盖与两种反馈的具体组织带来了实际收益。候选 A/B 是我最推荐优先加强的两个方向：它们直接把“造出更多/更难的数据”推进到“保持真正要学的决策，并把预算放在有效的经验上”。
